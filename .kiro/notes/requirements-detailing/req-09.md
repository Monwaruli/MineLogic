### Requirement 9: One Shared Measurement for Learner Feedback and Evaluation

**User Story:** As the researcher, I want the in-game feedback and the study outcome measures to come from the same code and the same stored data, so that assessment and evaluation are identical by construction.

#### Acceptance Criteria

1. WHEN the MineLogic client records the outcome of a Timed_Game, THE MineLogic client SHALL compute the game's Game_Metrics in one Metrics_Engine run and use that run's values, without recalculating any of them, for the learner's game summary, the Replay_Viewer's Logical_Move and Guess labels, and any leaderboard submission, stored game result, and Study_Record of that game.
2. FOR ALL full Boards and FOR ALL Move_Logs of games played to an outcome on those Boards, any two computations of the Game_Metrics with the same Metrics_Version SHALL produce identical Game_Metrics, including the same not-available values, the same partial mark, and the same count of Reveal_Actions excluded for Inexact_States, even when the two computations run in different supported browsers, on devices of different speeds, under different CPU loads, or with different browser locales and time zones (determinism property).
3. WHEN the MineLogic client stores a Timed_Game's Game_Metrics in the browser or in the Backend, THE MineLogic client SHALL store in the same write the Board identifier, the Board's canonical Board_Format text written by the Board_Printer, the Metrics_Version, and the Move_Log text written by the Move_Log_Serializer, including the End_Entry.
4. FOR ALL records stored in the browser or the Backend that contain Game_Metrics, including records labeled with a Metrics_Version earlier than the current one, parsing the stored Board_Format text with the Board_Parser, parsing the stored Move_Log text with the Move_Log_Parser against that Board, and computing the Game_Metrics with the stored Metrics_Version SHALL reproduce every stored Game_Metric value exactly, including not-available values and the partial mark, on any device and in any supported browser (recompute property).
5. THE Move_Log_Serializer SHALL write any Move_Log as text that declares its Move_Log format version and contains the Board identifier, each entry's action type, Tile, elapsed milliseconds, and Wasted_Click mark in Move_Log order, and, for a game that has ended, the End_Entry.
6. FOR ALL full Boards and FOR ALL Move_Logs that break none of the Move_Log_Parser rules for that Board, including Move_Logs with no entries, Move_Logs with Wasted_Click marks, Move_Logs without an End_Entry, and Move_Logs with an End_Entry for each of the outcomes Won, Lost, Timed_Out, and Interrupted, serializing with the Move_Log_Serializer and then parsing the text with the Move_Log_Parser against the same Board SHALL produce a Move_Log with the same Board identifier, the same entries in the same order with the same action type, Tile, time, and Wasted_Click mark, and the same End_Entry, and serializing that Move_Log again SHALL produce text identical to the first serialization (round-trip property).
7. IF Move_Log text parsed against a Board has a missing or unsupported format version, a missing Board identifier, a Board identifier that differs from that Board's identifier, an entry with an unknown action type, a Tile outside that Board, or no Wasted_Click mark, a time in an entry or in the End_Entry that is negative, not a whole number of milliseconds, or earlier than the preceding time, an End_Entry outcome other than Won, Lost, Timed_Out, or Interrupted, or an entry after the End_Entry, THEN THE Move_Log_Parser SHALL return no Move_Log and SHALL return an error that names the first failed rule in the text and, when that rule concerns an entry, the entry's position, counting the first entry as 1.
8. FOR ALL full Boards and FOR ALL Move_Logs recorded by playing those Boards, replaying the parsed Move_Log on the Board with the Board_Engine SHALL reproduce the original game's Board_State after every entry, every entry's Wasted_Click mark, and the final Board_State, and SHALL end with the original game's outcome and end time from the End_Entry, or with the game still in progress when the Move_Log has no End_Entry (replay property).
9. IF, while the Board_Engine replays a Move_Log on a full Board, the first entry is not a Reveal_Click on the Start_Tile, an entry is a Player_Action that the Board_Engine rejects because it conflicts with its Tile's state, an entry follows the entry that ended the game, an entry's Wasted_Click mark differs from whether the replayed action changed the Board_State, or the End_Entry records Won or Lost although the last entry did not end the game with that outcome at the End_Entry's time, records Timed_Out or Interrupted although an entry ended the game, or is missing although an entry ended the game, THEN THE Board_Engine SHALL stop the replay and return an error that names the failed rule and either the position of the offending entry, counting the first entry as 1, or the End_Entry.
10. IF the Metrics_Engine receives a Move_Log without an End_Entry, a Metrics_Version that it does not support, or inputs for which the Board_Parser, the Move_Log_Parser, or the replay returns an error, THEN THE Metrics_Engine SHALL return no Game_Metrics and SHALL return an error that names the missing End_Entry or the unsupported Metrics_Version, or that contains the underlying parser or replay error.
11. IF a write to the Backend contains Game_Metrics but lacks the Board identifier, the Board_Format text, the Metrics_Version, or the Move_Log text, THEN THE Backend SHALL reject the write, store none of its contents, and return the name of each missing item.
